# Architecture: AI + Tools — Why the Companion Needed Hands

## The Problem We Hit

Project Sub Three is an AI coaching companion for marathon runners. The companion talks to runners, learns about them, and builds personalized training plans. In our first version ("the skateboard"), the AI did everything in a single conversation response — it thought about the runner, updated their context, and generated the training plan, all in one streaming text output.

This worked for a 2-week starter plan. It was slow, but acceptable. Then we tried to build what runners actually need: a full training plan. 56+ weeks. 400+ individual workouts. Every day mapped out from today through race day.

Asking the AI to write all of that as JSON in a chat response was like asking someone to recite a phone book while having a conversation. It was slow (10+ seconds of streaming), error-prone (malformed JSON, wrong mileage), and fundamentally the wrong use of AI. The AI was spending 90% of its effort on mechanical, repetitive work — work that doesn't require intelligence.

## The Insight

A training plan is mostly deterministic. The plan follows a structure: phases build on each other, mileage progresses according to specific rules, rest weeks follow a pattern, workouts slot into specific days based on constraints. This isn't creative work. This is a lookup table with rules.

What IS creative work — what actually requires intelligence — is the coaching decisions:

- Where does this runner start? (Based on their current fitness, history, experience)
- Should any phases be compressed or extended? (Based on time to race, how they're progressing)
- How should the plan adapt when life happens? (Injury, illness, missed weeks)
- What changes when the runner asks for modifications? (And what are the consequences?)

Those decisions require understanding the runner, weighing tradeoffs, and making judgment calls. That's what AI is for.

## The Architecture: AI Decides, Tools Execute

We split the work:

**The AI companion** handles conversation, context-building, coaching decisions, and communication. It's the brain.

**The plan engine** (a TypeScript function) handles plan generation. It encodes the base training plan — 14 phases, every day of every week, workout types, mileage progression, rest week patterns — as a data structure. Given a starting point and a few parameters, it stamps out a complete plan in milliseconds.

**The bridge** is Claude's tool use capability. Mid-conversation, the AI can call `generate_training_plan` with its coaching decisions (start phase, start week, race date, adjustments). The tool runs server-side, generates the full plan instantly, and returns it. The AI then continues the conversation knowing what plan was created.

### The Flow

```
Runner sends message
    ↓
AI processes conversation, updates runner context
    ↓
AI decides it's time to generate a plan
    ↓
AI calls generate_training_plan(startPhase=1, startWeek=2, raceDate="2026-10-18")
    ↓
Plan engine runs (milliseconds) → full 54-week plan with 378 workouts
    ↓
Plan appears instantly in the Plan tab
    ↓
AI continues: "I've built your plan — check the Plan tab. 
               You're starting in Base Building and we'll work 
               through to race day in October."
```

### What the AI Provides (the coaching decisions)

```json
{
  "startPhaseIndex": 1,
  "startWeekInPhase": 2,
  "raceDate": "2026-10-18",
  "phaseAdjustments": [
    { "phaseIndex": 2, "action": "compress", "weeks": 2 }
  ]
}
```

### What the Tool Returns (the mechanical work)

A complete plan: 54 weeks, every day filled in, workouts assigned based on constraints (never adjacent to long runs, pull back near peak mileage), rest weeks calibrated to training load.

## Why This Matters Going Forward

This architecture isn't just about plan generation. It's the foundation for the living plan — the core product differentiator.

### Two-Way Plan Modifications

**Coach-initiated:** The AI monitors the runner's progress and calls `modify_training_plan` when it sees something that needs to change. Missed two weeks? The tool extends the current phase and recalculates. Crushing every workout? Compress a phase and move up.

**Runner-initiated:** "Can I move my long run to Sunday?" The AI calls the tool, the plan rebuilds, and — critically — the probability and injury risk numbers update immediately. The runner sees exactly what their change means for their goal.

### Real-Time Consequence Feedback

Because the plan is generated by a deterministic engine (not written by AI), we can recalculate instantly. Change one thing, see the ripple effect everywhere. This is what makes "the living plan" possible. If the AI had to regenerate a 56-week plan from scratch every time the runner moved a rest day, the experience would be unusable.

### The Skate-Bike-Car Evolution

This tool use architecture is the "bicycle" in our skate-bike-car progression:

- **Skateboard:** AI generates everything inline. Works for a prototype. Slow and fragile at scale.
- **Bicycle (now):** AI makes decisions, tools do the mechanical work. Fast, reliable, extensible.
- **Car (next):** Tools get smarter — integration with watch data (actual miles run), nutrition tracking, race registration, weather adjustments. Each new capability is a new tool the AI can call, without changing the core conversation flow.

The pattern scales. Every new feature becomes a tool, and the AI becomes more capable without getting more complex.

## Technical Details

### Plan Engine Files
- `app/lib/plan-engine/base-plan.ts` — The base training plan as a data structure (14 phases, pace constants, entry point logic)
- `app/lib/plan-engine/generator.ts` — Plan generation and workout assignment
- `app/lib/plan-engine/tool-definition.ts` — Claude tool definitions
- `app/lib/plan-engine/index.ts` — Public API

### API Route
- `app/api/chat/route.ts` — Handles streaming + tool use in a loop (text streams to client, tool calls execute server-side, results feed back to AI)

### Event Protocol
Tool results flow to the frontend via inline events in the text stream:
```
\n__EVENT__:{"type":"plan_generated","plan":{...}}\n
```
The frontend strips these from display and processes them as side effects.

### Key Numbers
- Full plan generation: ~5ms (vs 10-15 seconds for AI-generated)
- Plan size: 56 weeks, 392 daily workouts
- AI decision payload: ~100 bytes (vs ~15KB of plan JSON the AI used to write)
- Workout constraint violations: 0 (enforced by engine, not hoped for from AI)
